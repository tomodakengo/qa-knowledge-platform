# philosophy — なぜ issue ベースか

## tl;dr

- `.github/instructions/` Markdown は **枝を太くする土台**（昇格済みのナレッジ）
- GitHub Issues は **枝を生やす現場**（毎週・毎日生まれる原石）
- 両方が必要で、片方だけだと腐る

## Markdown だけで運用するとどう腐るか

`.github/instructions/ci-failure-analysis.instructions.md` のような Markdown ナレッジベースは、**書きはじめは綺麗** ですが、運用していくと以下の症状が出ます:

1. **更新権限が開発者寄りになる**: PR ベースの編集なので、QA 非エンジニア（手動テスター、ビジネス側の品質担当者）が直接コミットしづらい。結果、現場の知見が反映されない
2. **「最初の起票」が重い**: 失敗を見つけた人が「これパターン化すべきかな…まあいいか…」と先送りする。Markdown 1ファイルへの commit はカジュアルさが足りない
3. **議論の場がない**: 「これってバグ？それともパターン？」を議論する場が無いまま、誰かの独断でマージされる
4. **昇格基準が暗黙**: 「3回踏まれたら載せる」みたいな運用ルールが文書化されない

## Issues だけで運用するとどう腐るか

逆に Issues 単体に頼ると:

1. **検索しづらい**: ラベルでざっくり絞れるが、Pattern catalogue として "整備された一覧" にならない
2. **AI が読みにくい**: LLM に「このリポジトリの flaky パターン全部教えて」と聞くと open/closed を全部 fetch することになり token 効率が悪い
3. **古い議論が残る**: 解決済みの issue が混ざって、AI が混乱する

## 二段構えの設計

このリポジトリでは:

| 層 | 何が住むか | 誰が更新するか | AI が参照するか |
|---|---|---|---|
| GitHub Issues | 失敗起票、再現議論、未昇格の仮説 | 全員（QA / 開発 / ビジネス） | triage 時のみ（`gh issue list --label P-...`） |
| `.github/instructions/` | Hard bans、昇格済み Pattern catalogue | 昇格ワークフロー（人間レビュー必須） | 毎回（auto-heal pipeline 起動時） |

この二段構えにより:

- **カジュアルさ** は Issue で確保（思いついたら起票、ラベル誤りもOK）
- **品質ゲート** は昇格ワークフローで確保（confidence-high + 人間レビュー）
- **AI の token 効率** は instructions ファイルで確保（昇格済みだけ読む）

## "ナレッジ運用のリズム"

ナレッジは "1 度書く" ではなく "毎週育てる" 前提で設計する必要があります。

- **日次**: 失敗を踏んだ人が Issue 起票（5分以内、テンプレ任せ）
- **週次**: triage 担当が `status-confirmed` への昇格 / 重複統合 / `P-product-bug-suspect` のエスカレ
- **週次（cron）**: `confidence-high` Issue が instructions/ にマージされる PR を自動生成
- **月次**: 古い `status-promoted` Issue を archive、ラベル taxonomy を見直し

このリズムが回り続けるかぎり、ナレッジは腐りません。リズムが止まれば、AI は古い情報を読んで暴走します。

## 関連: AI4QA におけるこの設計の意義

`docs/ai4qa-rationale.md` で詳述します。要点だけ:

- AI4QA の本丸は「テスト生成」ではなく「ナレッジ運用」
- ナレッジを **書くコスト** より **腐らせないコスト** の方が高い
- このコストを下げる仕組みを最初から組み込んだリポジトリテンプレートが、本リポジトリの存在理由
